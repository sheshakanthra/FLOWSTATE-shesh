## Decisions

Record only decisions that are NOT obvious from reading the code. Format: `[session] decision — reason`.

- `[A1]` Font variable classNames (`switzer.variable`, `commitMono.variable`) are applied on `<html>`, not `<body>`. `--font-sans`/`--font-mono` are declared at `:root` inside `@theme` and reference `--font-switzer`/`--font-commit-mono`; a custom property's `var()` references are resolved once, where the property is declared, using values visible at that element — not re-resolved per consumer down the tree. Putting the font classes on `<body>` left `--font-switzer` invisible at `:root`, so `--font-sans` computed to guaranteed-invalid (empty) everywhere. Fixed by moving the classNames up to `<html>`.
- `[A1]` The `no-color-literals` ESLint rule only flags bare CSS named colors (e.g. `"red"`, `"blue"`) when the string is the value of a color-ish property/attribute (`color`, `background`, `fill`, `border*Color`, etc.) — not everywhere. `red` and `blue` are both valid CSS named colors *and* this codebase's semantic token names, so a blanket ban would break ordinary variant props like `variant="red"`. Hex and `rgb()`/`hsl()` literals are still caught unconditionally everywhere, matching the spec's "must fail CI" requirement without false-positiving on the vocabulary the design system itself uses.
- `[A1]` Semantic triples (`{color}-fg`/`-bg`/`-line`) get distinct, explicitly-computed hex/rgba values per theme rather than a live `color-mix()` formula. `-fg` is darkened per hue for light-mode AA contrast (the dark-mode hues are too light to read as text on a near-white background); `-bg`/`-line` are rgba tints of that same darkened hue. This satisfies the gate's "toggling theme changes every swatch" requirement for all fifteen semantic tokens, not just the neutrals.
- `[A1]` No `clsx`/`tailwind-merge` dependency — `lib/utils.ts` has a small dependency-free `cn()` instead, since neither package is in CLAUDE.md's approved dependency table.

- `[A6]` **Postgres role split — required for RLS to mean anything.** Docker's `POSTGRES_USER` env var bootstraps that role as a Postgres *superuser*, and superusers bypass row-level security unconditionally — `FORCE ROW LEVEL SECURITY` has no effect on them (it only overrides the lesser *table-owner* exemption). Discovered by writing the RLS proof test first and watching it fail (cross-workspace row was still visible) before ever manually confirming the policy worked. Fix: a second role, `kiln_app`, created by hand in the running container (`CREATE ROLE kiln_app LOGIN PASSWORD ...; GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES ...; ALTER DEFAULT PRIVILEGES ... GRANT ... FORCE ROW LEVEL SECURITY`) needs owner privileges `kiln_app` deliberately doesn't have. **A fresh non-Docker Postgres (or any managed Postgres) needs this same two-role setup by hand** — there's no migration for role creation since roles aren't database objects `drizzle-kit` manages, and a bootstrap superuser will exist under some name on most local setups even outside Docker.

- `[B4]` **A real, reproducible Postgres bug found and fixed: every RLS policy's `current_setting(..., true)::uuid` cast could crash on an unrelated, unscoped query.** Root cause: `current_setting(name, missing_ok)` only returns NULL when Postgres has *never once* seen that custom GUC name on the current backend connection — `lib/repos/db.ts`'s `withScope()` calls `set_config('app.workspace_id', ..., true)` (transaction-*local*) whenever a caller scopes by `workspaceId` alone (no `userId`), and once that's happened even once on a pooled connection, the GUC is "known," so a *later* transaction on that *same reused connection* that never sets it again gets back `''` (empty string), not NULL, the instant the earlier transaction's local scope expires at commit. `''::uuid` throws, not "zero rows." Reproduced deterministically standalone in under 15 lines: eight rapid `withScope({ workspaceId })` calls followed immediately by one `withScope({ userId })` call (`lib/repos/workspaces.ts`'s `getWorkspaceContext`) on the same process — every time. Never triggered before B4 because no earlier session's code opened several rapid, alternating single-key `withScope()` calls on a shared connection in one request; B4's run route is the first (`createRun` + up to N `recordStep` + `finishRun`, all `{ workspaceId }`-only, back to back). **Fixed at the RLS layer**, not by changing `withScope` itself: `db/migrations/0005_fix_rls_empty_string_cast.sql` wraps every policy's cast in `NULLIF(current_setting(...), '')::uuid`, converting the empty-string case back to a real NULL — restores the exact original fail-closed behavior (an empty/unscoped axis still can never match a real row) rather than loosening it; verified with a direct unscoped-query check (0 rows) after the fix, plus the existing RLS proof tests (`lib/repos/agents.test.ts`, `lib/repos/agents-graph.test.ts`) still pass. - `[B4]` **Loop does not really iterate.** A true loop would mean the orchestrator re-entering already-visited nodes once per item — a materially bigger feature (per-iteration step recording, subgraph re-execution) than a single-pass DAG walk supports, and none of B4's gate items exercise iteration count. `loop.ts`'s executor caps `items` at `maxIterations` and passes the (possibly truncated) array straight through as `item`, firing `done` immediately — single-pass, not a design a future session extending real iteration needs to work around, since `done` firing alone is still a coherent "the loop finished" signal either way.
- `[B4]` **`condition.ts`'s expression evaluator is a small hand-rolled recursive-descent parser (literals, `==`/`!=`/`>`/`<`/`>=`/`<=`, `&&`/`||`/`!`, parens) — deliberately not `eval`/`new Function`.** By the time a Condition node's `expression` reaches this executor, the orchestrator has already replaced every `{{token}}` with its real resolved value's literal text (`scope-resolver.ts`'s `interpolateConfig`), so the evaluator only ever needs to parse literals and comparisons, never variable lookups — arbitrary code execution from a text field isn't worth the risk for that. `transform.ts` similarly avoids `eval`: a dot-path accessor only (`resolvePath`), matching "reshaping arbitrary data" without needing a general expression language.
- `[B4]` **The orchestrator's branch-pruning contract: a `NodeExecutionResult.output` port simply absent from the returned object means "did not fire."** `Condition` returns only `{true: ...}` or `{false: ...}`, never both; `humanInLoop` returns only `{approved: ...}`. `shouldSkip()` (executor.ts) marks a node `skipped` only when *every* incoming edge is dead (source failed/skipped, or its port never fired) — a node fed by both a live and a dead branch still runs, the natural "OR merge" semantics for a convergence point (exercised directly: the seeded Recall Scheduler's Output node is reachable via both `condition.true` → `tool` → `output` and, structurally, `condition.false` → `output` directly, though only one path ever actually fires per run).
